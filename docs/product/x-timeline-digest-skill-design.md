# X 时间线每日摘要 Skill 设计方案（x-timeline-digest）

> 版本：v1.0（2026-08-18）
> 状态：设计评审稿
> 目标目录：`skills/x-timeline-digest/`
> 关联资产：`skills/morning-report/`（模板与自检范式）、`skills/zhihu-publish/scripts/chrome-utils.ts`（Chrome CDP 启动范式）、`.chrome-profile/`（仓库内独立 Chrome 用户目录）

---

## 1. 背景与目标

### 1.1 问题

X（Twitter）时间线信息密度高但噪音也大：广告、推广、水帖、重复转推混杂，逐条刷时间线既耗时又容易漏掉重要信息。

### 1.2 目标

构建一个 skill：每天自动（或手动触发）使用本地 Chrome 打开 `https://x.com/home`，采集**过去 24 小时**的时间线内容，过滤广告与低价值内容，分门别类、按个人信息优先级排序、统一翻译为中文，最终产出一篇带**原文摘录 + 可点击原文链接**的 Hugo 文章，实现：

1. **不漏** — 24 小时窗口内符合条件的内容全部收录；
2. **省时** — 读者只看分类排序后的中文摘要，无需刷原始时间线；
3. **可溯源** — 每条内容附 X 原文链接与原文摘录，一键跳转核实。

### 1.3 非目标

- 不发布、不点赞、不关注、不私信 — **只读**，不产生任何账号写操作；
- 不做跨平台聚合（本 skill 只处理 X 时间线）；
- 不绕过 X 的登录墙或付费墙获取未授权内容；
- 不存储、不上传任何账号凭据。

## 3. 采集层设计

### 3.1 浏览器方案

**复用项目既有 Chrome CDP 范式**（与 `zhihu-publish` 一致），不引入新依赖：

| 决策点 | 方案 | 理由 |
| ------ | ------ | ------ |
| 浏览器 | 本地 Google Chrome（真实用户浏览器） | X 对无头/自动化浏览器风控严格，真实 Chrome + 真人登录态最稳定 |
| 登录态 | 独立用户目录 `.chrome-profile/`（仓库内已存在） | 一次登录长期复用；与日常浏览器隔离，避免抢占用户正在使用的窗口 |
| 控制协议 | CDP（`--remote-debugging-port` + `baoyu-chrome-cdp`） | 与 `zhihu-publish/scripts/chrome-utils.ts` 同源，维护成本最低 |
| 反检测 | `--disable-blink-features=AutomationControlled` + 拟人化节奏 | 降低被判定为自动化的风险 |
| 沙箱环境 | `--no-sandbox --disable-gpu` + 启动前清理 `SingletonLock/Socket/Cookie` | 沿用 `chrome-utils.ts` 已验证的沙箱兼容做法 |

**启动参数基线**（继承 chrome-utils.ts 模式）：

```text
--user-data-dir=<repo>/.chrome-profile
--remote-debugging-port=<自动空闲端口>
--no-sandbox --disable-gpu
--disable-blink-features=AutomationControlled
https://x.com/home
```

### 3.2 采集流程

```
1. 启动 Chrome → 打开 https://x.com/home
2. 登录态检查（见 3.3）
3. 切换到「正在关注（Following）」时间线 Tab
   （默认推荐流「For you」混入大量非关注内容，不符合"我的时间线"语义）
4. 循环滚动采集：
   a. 读取当前视口内推文 article 节点
   b. 解析每条推文字段（见 3.4）
   c. 判定时间戳：
      - ≥ 24h 前 → 停止滚动，采集结束
      - 在窗口内 → 记录并继续滚动
   d. 连续 N 次滚动无新推文 → 判定到达底部/被限流，按异常处理（§7）
5. 原始数据写入 raw-YYYY-MM-DD.json
```

**滚动节奏（拟人化硬约束）**：

- 每次滚动间隔 2–5 秒随机（禁止无间隔死循环滚动）；
- 单次运行滚动上限 60 次（可配置），超限仍未触达 24h 边界时：保存现场、标注「窗口未闭合」进入人工确认分支；
- 单次运行总时长上限 15 分钟（看门狗超时自动保存并退出）。

### 3.3 登录态检查

- 打开页面后检测是否出现登录表单/跳转 `x.com/i/flow/login`；
- **skill 绝不自动输入账号密码**。未登录时：浏览器窗口保持打开，向用户报告「请在打开的 Chrome 窗口中手动登录 X，登录后重新运行」；
- 检测到验证码/异常验证页：同样停下等待人工处理，不尝试绕过。

### 3.4 采集字段

每条推文记录以下结构化字段（选择器失效时以 `aria-label` 与 `<time datetime>` 为兜底锚点）：

| 字段 | 说明 | 用途 |
| ------ | ------ | ------ |
| `post_id` | 推文唯一 ID（从 permalink 解析） | 去重、链接构造 |
| `permalink` | `https://x.com/<user>/status/<id>` | 原文链接 |
| `author_handle` / `author_name` | 作者 | 展示、优先级加权 |
| `is_retweet` / `retweeted_by` | 是否转推及转推者 | 去重、过滤判定 |
| `is_promoted` | 是否广告（Promoted/推广标记） | 过滤 |
| `timestamp` | ISO 8601（来自 `<time datetime>`） | 时间窗判定 |
| `text` | 推文全文（长推展开后） | 摘要与翻译 |
| `lang` | 语言（DOM lang 属性 + 启发式） | 翻译判定 |
| `quoted_post` | 引用推文内容与其链接（若有） | 完整性 |
| `media_summary` | 图片 alt 文本/视频描述（如有） | 信息补充；**不下载媒体** |
| `link_cards` | 推文内外部链接 | 溯源、价值判定 |

**不采集**：私信、通知、书签、媒体文件本体、其他用户的非公开数据。

### 3.5 时间窗语义

- 窗口 = `[运行时刻 - 24h, 运行时刻]`，以推文**原始发布时间**为准（转推按原推时间，但显示转推者）；
- X 时间线显示相对时间（"2小时"），必须解析 `<time>` 元素的 `datetime` 绝对值；
- 置顶推文（Pinned）通常超窗，按时间戳正常过滤，不做特判。

## 4. 处理层设计

### 4.1 过滤规则（三级漏斗）

**L1 — 硬过滤（规则判定，零容忍）**：

| 类型 | 判定信号 |
| ------ | ------ |
| 广告 | `is_promoted` 标记；"Ad/推广" 文案 |
| 纯转推重复 | 同一原推被多人转推，只保留 1 条（优先保留关注优先级最高的转推者） |
| 时间窗外 | 原始发布时间早于窗口起点 |
| 无法溯源 | 无有效 permalink 的条目 |

**L2 — 低价值过滤（启发式 + LLM 辅助判定）**：

- 纯表情/单句情绪宣泄、无信息增量（"太棒了""冲！"类）；
- 纯营销引流（加密喊单、带货链接、抽奖转发）；
- 与本人关注领域完全无关的日常闲聊；
- 纯互推/点赞求关注类内容。

**L3 — 保留判定**：凡命中任一保留信号即收录 ——

- 技术/产品发布、开源项目、模型更新；
- 行业观点、数据、研究报告、融资消息；
- 本人高频关注作者的实质内容（即使简短）；
- 有外部链接且链接指向实质文章/仓库/论文。

> 判定原则：**宁松勿枉**。拿不准的进入「待人工复核」清单在文末单列，不静默丢弃。

### 4.2 分类体系

固定 7 个一级分类（可为空，空分类不输出）：

| 分类 | 覆盖内容 |
| ------ | ------ |
| 🤖 AI 与技术 | 模型、工具、开源项目、工程实践 |
| 💰 市场与投资 | 宏观、加密、美股、融资 |
| 🚀 产品与创业 | 产品发布、独立开发、商业模式 |
| 🌍 行业与资讯 | 政策、公司动态、行业新闻 |
| 💡 观点与思考 | 长文观点、方法论、经验分享 |
| 🛠️ 资源与工具 | 教程、清单、可复用资源 |
| 📌 其他值得关注 | 以上无法归入但通过过滤的内容 |

### 4.3 优先级评分模型

每条推文打分（0–100），分数决定**分类内的排序**与「今日头条」选取：

```
score = 作者权重(0-35) + 内容价值(0-35) + 互动信号(0-15) + 时效加成(0-15)
```

| 维度 | 说明 |
| ------ | ------ |
| 作者权重 | 来自 `profile.json` 的分级关注列表：核心关注 35 / 常规关注 20 / 一般关注 8；陌生作者（经转推进入）≤ 5 |
| 内容价值 | LLM 评估信息密度：有数据/结论/链接/代码 > 观点 > 转述 |
| 互动信号 | 互动量在同批采集中的相对分位（归一化，避免刷量账号霸榜；仅参考不主导） |
| 时效加成 | 越接近运行时刻加成越高（6h 内满分，线性衰减） |

**评分 ≥ 85 的条目进入文首「今日头条」区（最多 3 条）。**

### 4.4 翻译规范

- `lang != zh` 的推文，摘要与原文摘录均翻译为中文；
- 专有名词保留原文并在首次出现时括注中文（如 "Claude Code（克劳德代码）"；业界通用名如 GitHub、Chrome 不译）；
- 翻译忠实于原文，**禁止增补原文没有的事实、数字、判断**；
- 原文语言为中文的条目不翻译，但摘要仍按统一风格提炼。

### 4.5 个人偏好配置

`references/profile.json`（skill 内可版本管理，敏感项留空不入库）：

```json
{
  "priority_authors": { "tier1": ["@handle1"], "tier2": ["@handle2"], "tier3": [] },
  "interest_domains": ["AI Agent", "量化交易", "独立开发"],
  "muted_keywords": ["airdrop", "giveaway"],
  "max_posts_per_day": 40,
  "timeline_tab": "following"
}
```

## 5. 生成层设计

- 按 `references/template.md` 渲染（模板骨架见 §6），与 `morning-report` 的文章风格保持一致；
- 每条内容三要素齐备：**中文摘要（2–3 句实质提炼）+ 原文摘录（中文原文或译文，≤3 行）+ 原文链接 `[原文](https://x.com/<user>/status/<id>)`**；
- 文末附「采集报告」：总数、过滤数、各分类数、窗口是否闭合、待复核清单。

## 6. 输出规范（Hugo 文章）

### 6.1 Frontmatter（对齐项目既有规则）

```yaml
---
title: "X时间线精选 YYYY-MM-DD"
date: YYYY-MM-DDTHH:MM:SS+08:00   # = 实际写入磁盘时刻 - 5 分钟，禁止填计划发布时刻
slug: x-timeline-digest-YYYY-MM-DD
description: "YYYY年MM月DD日 X 时间线 24 小时精选：AI、市场与创业领域值得关注的 N 条内容。"
draft: false
categories: ["行业快讯"]
tags: ["X精选", "时间线", "AI", "资讯"]   # 2-5 个精准名词
hiddenFromHomePage: true
---
```

> `date` 硬性规则沿用 morning-report 既有约定：`date = 写入磁盘时刻 − 5min`，推荐公式
> `TZ=Asia/Shanghai date -v-5M "+%Y-%m-%dT%H:%M:%S+08:00"`，否则 Hugo 构建会判为「未来页面」整篇排除。

输出路径：`content/posts/news/x-timeline-digest-YYYY-MM-DD.md`（文件名 = slug.md）。

### 6.2 正文模板

```markdown

| 指标 | 数值 |
```

### 6.3 链接格式

- 原文链接固定 `[原文](https://x.com/<user>/status/<id>)`，禁止裸 URL、禁止指向 `x.com/home` 等聚合页；
- 引用推文需同时给出引用对象链接。

## 7. 异常处理

| 情况 | 处理策略 |
| ------ | ------ |
| 未登录 / 登录失效 | 停，等待人工在浏览器窗口登录；不自动输入凭据 |
| 出现验证码 / 风控拦截 | 停，报告用户；连续 2 天命中则建议降低运行频率 |
| 滚动 60 次未触达 24h 边界 | 保存现场，文内标注「窗口未闭合，实际覆盖 X 小时」 |
| DOM 结构变更导致解析失败 | 截图存证 + 报告；采集脚本选择器集中在一个常量区便于修复 |
| 24h 内零条有效内容 | 仍生成文章，如实报告「今日无符合条件内容」，不硬凑 |
| 重复运行（同日） | 覆盖同日产物；靠 `seen-post-ids.json` 防止跨日重复收录 |
| Chrome 启动失败 | 清理 profile 锁文件后重试一次；仍失败则报错退出 |
| 网络中断 | 指数退避重试 3 次后终止，保存已采集部分 |

## 8. 安全与合规设计

### 8.1 凭据安全

- **skill 任何位置不存储、不读取、不传输账号密码与 Cookie 文件**；登录态完全依赖本地 Chrome 用户目录；
- `profile.json` 只含公开 handle 与兴趣词，不含私密信息；
- 采集产物（raw/filtered JSON）仅存本地 `tmp` 目录，不入 Git、不上传。

### 8.2 账号安全

- 严格只读：不执行点赞、关注、发帖、私信等任何写操作，避免触发风控；
- 拟人化节奏（§3.2）：随机滚动间隔、单次运行上限，把访问模式控制在真人浏览水平；
- 运行频率默认每日 1 次；更高频率需显式确认。

### 8.3 内容安全

- 仅采集本人登录后「正在关注」时间线的公开可见内容；
- 产出文章为摘要 + 短摘录 + 链接，不构成全文转载；
- 涉政、涉暴等敏感内容默认进入过滤，如用户需要可在 `profile.json` 中显式放开。

### 8.4 合规提示

自动化浏览需遵守 X 服务条款与 robots/速率限制约束；本 skill 以个人低频只读使用为前提。若 X 明确禁止此类访问或账号收到警告，应停止使用并改用官方 API 或 RSS 方案。

## 9. 定时运行

- 首选：复用项目现有 cron/WorkBuddy automation 机制，每日固定时刻（建议 08:00 前，与早报错峰）以提示词触发 skill；
- 触发词：「X 精选」「时间线摘要」「x digest」「刷一下 X」「X 日报」；
- 运行后自动执行 git push（push 失败则 `git pull --rebase` 重试），push 成功才回报完成。

## 10. 验收标准（自检清单）

| 检查项 | 要求 |
| ------ | ------ |
| 时间窗口 | 所有收录条目原始发布时间在 24h 内，或明确标注窗口未闭合 |
| 广告清零 | 正文无任何 Promoted/推广内容 |
| 链接真实 | 每条 `[原文](url)` 均可打开且指向对应推文（发布前逐条核验） |
| 三要素完整 | 每条含摘要 + 原文摘录 + 原文链接，缺一不可 |
| 翻译质量 | 非中文内容全部翻译；专有名词处理合规；无臆造事实 |
| frontmatter | date ≤ 写入时刻 − 5min；含 `draft: false` 与 `hiddenFromHomePage: true`；slug 符合固定模式 |
| 只读承诺 | 运行全程无点赞/关注/发帖等写操作 |
| 采集报告 | 文末统计数与正文条目数一致 |

## 11. 实施路线

| 阶段 | 交付物 | 验收 |
| ------ | ------ | ------ |
| P0 采集打通 | `collect-timeline.ts` + 登录态检查 | 手动运行一次，产出 raw JSON 且窗口闭合 |
| P1 处理链路 | 过滤/分类/评分/翻译提示词与规则文件 | 对一次真实采集产出 filtered JSON，人工抽查 10 条判定合理 |
| P2 文章生成 | template.md + Hugo 输出 | 生成文章通过 §10 自检并成功构建预览 |
| P3 定时与健壮性 | cron 接入 + 异常分支演练 | 连续 3 天无人值守运行成功 |

### 11.1 备选方案（风险预案）

| 风险 | 备选 |
| ------ | ------ |
| X DOM 频繁变更导致采集脚本持续维护成本高 | 改用页面内置数据流（`window.__INITIAL_STATE__` / GraphQL 响应拦截）作为解析兜底 |
| 风控趋严无法稳定浏览 | 降级为官方 X API（Basic 套餐时间线读取）；或用户手动导出后离线处理 |
| 内容量过大单日超 40 条 | 按评分截断，文末标注「另有 N 条低优先级内容未收录」 |
