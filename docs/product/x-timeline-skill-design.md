# X 时间线每日摘要 Skill 设计方案（x-timeline）

> 版本：v1.2（2026-08-18，第二轮对抗性审查修订）
> 状态：设计评审稿
> 目标目录：`skills/x-timeline/`
> 关联资产：`skills/morning-report/`（模板与自检范式）、`skills/zhihu-publish/scripts/chrome-utils.ts`（Chrome CDP 启动范式）、`.chrome-profile/`（仓库内独立 Chrome 用户目录，已被 `.gitignore` 覆盖）

---

## 1. 背景与目标

### 1.1 问题

X（Twitter）时间线信息密度高但噪音也大：广告、推广、水帖、重复转推混杂，逐条刷时间线既耗时又容易漏掉重要信息。

### 1.2 目标

构建一个 skill：每天自动（或手动触发）使用本地 Chrome 打开 `https://x.com/home`，采集**过去 24 小时**的时间线内容，过滤广告与低价值内容，分门别类、按个人信息优先级排序、统一翻译为中文，最终产出一篇带**原文摘录 + 可点击原文链接**的 Hugo 文章，实现：

1. **不漏** — 24 小时窗口内符合条件的内容全部收录（窗口必须闭合，见 §3.2）；
2. **省时** — 读者只看分类排序后的中文摘要，无需刷原始时间线；
3. **可溯源** — 每条内容附 X 原文链接与原文摘录，一键跳转核实。

### 1.3 非目标

- 不发布、不点赞、不关注、不私信 — **只读**，不产生任何账号写操作；
- 不做跨平台聚合（本 skill 只处理 X 时间线）；
- 不绕过 X 的登录墙或付费墙获取未授权内容；
- 不存储、不上传任何账号凭据。

### 1.4 设计原则（第一性原理）

从"重要信息零遗漏 × 阅读成本最小化"派生六条本质需求，作为所有取舍的裁决依据：

| 需求 | 含义 |
| ------ | ------ |
| 窗口完备 | 采集必须**保证**覆盖完整 24h，"窗口未闭合"只能是故障而非正常态 |
| 过滤精准 | 宁松勿枉，拿不准不静默丢弃 |
| 有序呈现 | 重要内容先被看到 |
| 可溯源 | 链接与摘录构造可追溯到采集数据，禁止猜测 |
| 账号零风险 | 只读、拟人化、凭据不出本机 |
| 低维护成本 | 优先使用结构稳定的数据源，减少跟随前端改版 |

## 2. 总体架构

```
① 采集层               ② 处理层              ③ 输出层
Chrome + CDP           合并去重 → 硬过滤      Hugo Markdown
GraphQL 响应拦截(主)    → LLM 三分类          + 自检 + push
DOM 滚动(兜底)          → 分层排序 → 翻译
     │                      │                      │
.chrome-profile        filter/category 规则     content/posts/news/
(登录态复用)            + profile.json(偏好)      x-timeline-digest-*.md
```

三层职责单一、可独立重跑：采集失败可重试，处理失败不需重新采集（中间产物 JSON 落盘），输出失败不需重新处理。

## 3. 采集层设计

### 3.1 浏览器方案

**复用项目既有 Chrome CDP 范式**（与 `zhihu-publish` 一致），不引入新依赖：

| 决策点 | 方案 | 理由 |
| ------ | ------ | ------ |
| 浏览器 | 本地 Google Chrome（真实用户浏览器） | X 对无头/自动化浏览器风控严格，真实 Chrome + 真人登录态最稳定 |
| 登录态 | 独立用户目录 `.chrome-profile/`（仓库内已存在） | 一次登录长期复用；与日常浏览器隔离，避免抢占用户正在使用的窗口 |
| 控制协议 | CDP（`--remote-debugging-port` + `baoyu-chrome-cdp`） | 与 `zhihu-publish/scripts/chrome-utils.ts` 同源，维护成本最低 |
| 反检测 | `--disable-blink-features=AutomationControlled` + 拟人化节奏 | 降低被判定为自动化的风险 |
| 沙箱环境 | `--no-sandbox --disable-gpu` + 启动前清理 `SingletonLock/Socket/Cookie` | 沿用 `chrome-utils.ts` 已验证的沙箱兼容做法 |

**启动参数基线**（继承 chrome-utils.ts 模式）：

```text
--user-data-dir=<repo>/.chrome-profile
--remote-debugging-port=<自动空闲端口>      # 仅绑定 127.0.0.1（Chrome 默认行为，禁止手动改为对外地址）
--no-sandbox --disable-gpu
--disable-blink-features=AutomationControlled
https://x.com/home
```

### 3.2 采集主路径：GraphQL 响应拦截（v1.1 升级为主路径）

**为什么**：X Web 前端本身通过 GraphQL 接口加载时间线（「正在关注」Tab 对应 `HomeLatestTimeline` 查询）。拦截这些响应直接得到结构化 JSON，相比 DOM 滚动解析有四个结构性优势：

1. **窗口必然闭合** — 按游标（cursor）分页，直到某页数据的最早入场时间越过窗口起点即停（入场时间定义见 §3.5）；若某页有数据但无底部游标，判定时间线穷尽，等价闭合（raw JSON 记录 `closed_reason`）；不存在"滚动次数上限导致窗口未闭合"；
2. **数据精确** — 时间戳为精确 ISO 8601、推文全文无需展开长文、转推/引用/广告标记均为显式字段；
3. **快** — 全程约 1 分钟（DOM 滚动需 5–15 分钟），访问时长与风控暴露面同步下降；
4. **少维护** — JSON 字段名比 DOM 选择器稳定得多。

**流程**：

```
1. 启动 Chrome → 打开 https://x.com/home，CDP 开启网络响应监听
2. 登录态检查（见 3.4）
3. 切换到「正在关注（Following）」Tab
   （「For you」混入大量非关注内容，不符合"我的时间线"语义）
4. 拦截 HomeLatestTimeline 响应，解析推文条目与底部游标，按 post_id 当次去重，增量写入 raw JSON
5. 翻页边界判定（以条目入场时间为准，见 §3.5 时间窗语义）：
   页内最早入场时间仍在窗口内 → 触发下一次加载（滚动一次驱动），回到 4
   已越过窗口起点 → 采集结束（窗口闭合）
6. 收尾：保存截图存证，输出采集统计
```

**节奏硬约束**：翻页间隔 2–5 秒随机；总时长看门狗 10 分钟；连续 3 次响应为空或报错视为被限流，按 §6 处理。

**从响应中提取的关键字段**（字段名以实际接口为准，集中在脚本常量区便于修复）：`rest_id`（推文 ID）、`legacy.created_at`、`legacy.full_text`、作者 handle/name、`is_promoted` 类广告标记、转推/引用嵌套结构、互动计数、外部链接卡片。

### 3.3 兜底路径：DOM 滚动采集

当拦截路径连续失败（接口签名变化、响应结构大改）时自动降级：滚动 `x.com/home` 的 Following 视图，解析 `article` 节点，以 `<time datetime>` 绝对时间判定窗口边界。兜底路径接受「窗口未闭合」可能性，但必须在文内显式标注实际覆盖时长。两条路径共用 §3.5 字段规范。

### 3.4 登录态检查（含运行中失效检测）

- 打开页面后检测是否出现登录表单或跳转 `x.com/i/flow/login`；
- **skill 绝不自动输入账号密码**。未登录时：浏览器窗口保持打开，报告「请在打开的 Chrome 窗口中手动登录 X，登录后重新运行」；
- 检测到验证码/异常验证页：停下等待人工处理，不尝试绕过；
- **运行中失效检测**：每批数据校验登录态（拦截路径下接口返回 401/登录重定向即判定失效），立即停止并保存已采集部分，防止脏数据混入。

### 3.5 采集字段规范（两条路径统一）

| 字段 | 说明 | 用途 |
| ------ | ------ | ------ |
| `post_id` | 推文唯一 ID | 去重、链接构造 |
| `permalink` | `https://x.com/<user>/status/<id>`，由采集数据直接构造 | 原文链接 |
| `author_handle` / `author_name` | 作者 | 展示、排序加权 |
| `is_retweet` / `retweeted_by` | 是否转推及转推者 | 去重、过滤判定 |
| `is_promoted` | 是否广告 | 过滤 |
| `entry_created_at` | 入场时间：普通推为发布时间，转推为转推动作时间（外层 `created_at`） | 时间窗判定与翻页边界（见下方语义） |
| `created_at` | 原推发布时间（`legacy.created_at`，格式为 `EEE MMM dd HH:mm:ss Z yyyy`，非 ISO，需解析） | 展示「原帖发布于 X 前」 |
| `text` | 推文全文 | 摘要与翻译 |
| `lang` | CJK 字符占比启发式 + LLM 复核（不依赖 DOM lang 属性，X 的该属性不可靠） | 翻译判定 |
| `in_reply_to_status_id` | 所回复推文 ID | thread 链式合并（见 §4.1） |
| `quoted_post` | 引用推文内容与其链接（若有） | 完整性、去重 |
| `media_summary` | 图片 alt 文本/视频描述（如有） | 信息补充；**不下载媒体** |
| `link_cards` | 推文内外部链接 | 溯源、价值判定 |

**时间窗语义（双时间轴，v1.2 修正）**：窗口 = `[运行时刻 - 24h, 运行时刻]`。

- **收录与翻页边界一律用「入场时间」**：3 天前的旧帖被 2 小时前转推，是用户最近 24h 真实看到的内容——若按原推时间判定，既会漏收该条，又会让翻页边界提前误判"窗口已闭合"而漏采后续全部新帖；
- **原推发布时间仅用于展示**（标注「原帖发布于 3 天前」），同时展示转推者身份，不参与窗口判定。

**不采集**：私信、通知、书签、媒体文件本体、其他用户的非公开数据。

## 4. 处理层设计

### 4.1 合并与去重（过滤前的结构规整）

| 规则 | 处理 |
| ------ | ------ |
| Thread（连发长帖） | 依据 `in_reply_to_status_id` 把同一作者的连续回复链合并为一个条目：摘要覆盖全串要点，链接指向串首推 |
| 重复转推 | 同一原推被多人转推，只保留 1 条（优先保留关注层级最高的转推者） |
| 引用对撞 | 原推与其引用推同时在窗口内，保留原推，丢弃引用推（除非引用本身有独立增量信息） |
| 当次重复 | X 可能跨页返回重复条目，按 `post_id` 当次去重 |
| 跨日重复 | 命中 `seen-post-ids.json`（滚动保留 90 天）的条目标记并丢弃 |

### 4.2 过滤漏斗

**L1 — 硬过滤（规则判定，零容忍）**：广告（`is_promoted`/"Ad/推广"文案）、入场时间窗外、无有效 permalink、墓碑条目（原帖已删除/账号不可用的占位项）。

**L2 — LLM 三分类**：对 L1 幸存者逐条判定 ——

| 判定 | 标准 |
| ------ | ------ |
| 收录 | 命中任一保留信号：技术/产品发布、开源项目、模型更新；行业观点、数据、研究报告、融资消息；`profile.json` 核心关注作者的实质内容；有指向实质文章/仓库/论文的外部链接 |
| 待复核 | 价值拿不准（宁松勿枉，文末单列，不静默丢弃） |
| 丢弃 | 纯情绪宣泄无信息增量、纯营销引流（喊单/带货/抽奖）、与关注领域无关的闲聊、互推求关注 |

> 效率约束：条目分批判定（每批约 50 条）控制 LLM 调用量；LLM 之前先做廉价预筛（如纯表情、无链接的超短文本），预筛规则必须保守，拿不准一律放行给 LLM。

### 4.3 分类体系

固定 7 个一级分类（可为空，空分类不输出）：

| 分类 | 覆盖内容 |
| ------ | ------ |
| 🤖 AI 与技术 | 模型、工具、开源项目、工程实践 |
| 💰 市场与投资 | 宏观、加密、美股、融资 |
| 🚀 产品与创业 | 产品发布、独立开发、商业模式 |
| 🌍 行业与资讯 | 政策、公司动态、行业新闻 |
| 💡 观点与思考 | 长文观点、方法论、经验分享 |
| 🛠️ 资源与工具 | 教程、清单、可复用资源 |
| 📌 其他值得关注 | 以上无法归入但通过过滤的内容 |

### 4.4 排序模型（v1.1 简化，替代原四维评分）

取消 0–100 打分制（魔法数字多、互动量维度噪音大且不可复现），改为两级排序键：

1. **作者层级**（主键）：`profile.json` 核心关注 > 常规关注 > 一般关注 > 陌生作者（经转推进入）；
2. **信息密度**（次键）：LLM 判定——有数据/结论/链接/代码 > 独立观点 > 转述评论。

**今日头条**：由 LLM 从「核心关注作者 + 高信息密度」条目中直接推选最多 3 条置于文首，不做阈值截断。

### 4.5 翻译与原文呈现（v1.1 修订）

- `lang != zh` 的推文：摘要与主摘录使用**中文译文**；同时在 `<details>` 折叠块中保留**原文原貌**（LoveIt 主题支持 details 渲染），满足"看原文"的忠实性需求；
- 专有名词保留原文并在首次出现时括注中文（业界通用名如 GitHub、Chrome 不译）；
- 翻译忠实于原文，**禁止增补原文没有的事实、数字、判断**；
- 中文推文不翻译，摘要仍按统一风格提炼；
- 折叠原文默认开启，可在 `profile.json` 中关闭。

### 4.6 个人偏好配置

`references/profile.json`（skill 内可版本管理，敏感项留空不入库）：

```json
{
  "priority_authors": { "tier1": ["@handle1"], "tier2": ["@handle2"], "tier3": [] },
  "interest_domains": ["AI Agent", "量化交易", "独立开发"],
  "muted_keywords": ["airdrop", "giveaway"],
  "max_posts_per_day": 40,
  "timeline_tab": "following",
  "show_original_in_details": true
}
```

## 5. 输出规范（Hugo 文章）

按 `references/template.md` 渲染，风格与 `morning-report` 保持一致。每条内容要素齐备：**中文摘要（2–3 句实质提炼）+ 原文摘录（译文，≤3 行；非中文条目附 `<details>` 原文）+ 原文链接**。文末附「采集报告」（统计与待复核清单）。

### 5.1 Frontmatter（对齐项目既有规则）

```yaml
---
title: "X时间线精选 YYYY-MM-DD"
date: YYYY-MM-DDTHH:MM:SS+08:00   # = 实际写入磁盘时刻 - 5 分钟，禁止填计划发布时刻
slug: x-timeline-digest-YYYY-MM-DD
description: "YYYY年MM月DD日 X 时间线 24 小时精选：AI、市场与创业领域值得关注的 N 条内容。"
draft: false
categories: ["行业快讯"]
tags: ["X精选", "时间线", "AI", "资讯"]   # 2-5 个精准名词
hiddenFromHomePage: true
---
```

> `date` 硬性规则沿用 morning-report 既有约定：`date = 写入磁盘时刻 − 5min`，推荐公式
> `TZ=Asia/Shanghai date -v-5M "+%Y-%m-%dT%H:%M:%S+08:00"`，否则 Hugo 构建会判为「未来页面」整篇排除。

输出路径：`content/posts/news/x-timeline-digest-YYYY-MM-DD.md`（文件名 = slug.md）。

```markdown
（同上结构，空分类省略）

| ------ | ------ |
```

### 5.3 链接规范与核验（v1.1 修订）

- 原文链接固定 `[原文](https://x.com/<user>/status/<id>)`，禁止裸 URL、禁止指向 `x.com/home` 等聚合页；
- permalink 一律由采集数据中的 `post_id` 构造，**禁止猜测或拼接**——准确性在采集时结构性保证；
- 因此不再逐条打开核验（避免重复暴露账号行为）：发布前仅**抽查 3 条**实开确认跳转正确（由 Browser 直接执行，不单设脚本）；引用推文需同时给出引用对象链接。

## 6. 异常处理

| 情况 | 处理策略 |
| ------ | ------ |
| 未登录 / 登录失效（含运行中失效） | 停，保存已采集部分，等待人工登录；不自动输入凭据 |
| 出现验证码 / 风控拦截 | 停，报告用户；连续 2 天命中则建议降低运行频率 |
| GraphQL 拦截路径失效 | 自动降级 DOM 滚动兜底路径（§3.3）；两条路径均失败则报错退出 |
| 兜底路径仍未触达 24h 边界 | 保存现场，文内标注「窗口未闭合，实际覆盖 X 小时」 |
| 接口/页面结构变更导致解析失败 | 截图存证 + 报告；解析字段集中在脚本常量区便于修复 |
| 24h 内零条有效内容 | 仍生成文章，如实报告「今日无符合条件内容」，不硬凑 |
| 定时运行失败（区别于零内容） | 30 分钟后自动重试 1 次；二次失败仅报告不产出文章，避免空窗假象 |
| 重复运行（同日） | 直接重新采集（主路径约 1min；复用旧 raw 会因窗口滑动漏掉新内容）；同日产物覆盖 |
| 重复收录（跨日） | `seen-post-ids.json` 指纹拦截，文件滚动保留 90 天防无界增长 |
| Chrome 启动失败 | 清理 profile 锁文件后重试一次；仍失败则报错退出 |
| 网络中断 | 指数退避重试 3 次后终止，保存已采集部分 |
| 进程中途崩溃 | raw JSON 逐页增量落盘，重跑时按已有数据的最早入场时间续采 |

## 7. 安全与合规设计

### 7.1 凭据安全

- **skill 任何位置不存储、不读取、不传输账号密码与 Cookie 文件**；登录态完全依赖本地 Chrome 用户目录；
- `.chrome-profile/` 内含登录态，**等效账号凭据**：已确认 `.gitignore` 第 91 行覆盖该目录；首次部署到新环境时必须复核此覆盖；
- `profile.json` 只含公开 handle 与兴趣词，不含私密信息；
- 采集产物（raw/filtered JSON）仅存本地 `.workbuddy/tmp`（已被 `.gitignore` 覆盖），不入 Git、不上传；
- CDP 调试端口仅绑定 `127.0.0.1`，禁止对外暴露。

### 7.2 账号安全

- 严格只读：不执行点赞、关注、发帖、私信等任何写操作，避免触发风控；
- 拟人化节奏（§3.2）：随机翻页间隔、单次运行时长看门狗，访问模式控制在真人浏览水平；
- 运行频率默认每日 1 次；更高频率需显式确认。

### 7.3 内容安全

- 仅采集本人登录后「正在关注」时间线的公开可见内容；
- 产出文章为摘要 + 短摘录 + 链接，不构成全文转载；
- 涉政、涉暴等敏感内容默认进入过滤，如用户需要可在 `profile.json` 中显式放开；
- LLM 分类/翻译会将时间线内容发送给模型服务方（数据出站）：个人使用场景可接受（与 morning-report 等既有 skill 一致），但调用内容仅限推文文本，禁止附带任何凭据信息。

### 7.4 合规提示

自动化浏览需遵守 X 服务条款与速率限制约束；本 skill 以个人低频只读使用为前提。若 X 明确禁止此类访问或账号收到警告，应停止使用并改用官方 API 或 RSS 方案。

## 9. 验收标准（自检清单）

| 检查项 | 要求 |
| ------ | ------ |
| 时间窗口 | 主路径必须闭合；兜底路径未闭合时文内显式标注覆盖时长 |
| 时间基准 | 收录与边界判定均按入场时间；旧帖新转条目未被误裁 |
| 广告清零 | 正文无任何 Promoted/推广内容 |
| 链接真实 | permalink 全部由采集数据构造（可溯源）+ 抽查 3 条实开通过 |
| 条目要素完整 | 每条含摘要 + 原文摘录 + 原文链接；非中文条目附 details 原文 |
| 翻译质量 | 非中文内容全部翻译；专有名词处理合规；无臆造事实 |
| frontmatter | date ≤ 写入时刻 − 5min；含 `draft: false` 与 `hiddenFromHomePage: true`；slug 符合固定模式 |
| 只读承诺 | 运行全程无点赞/关注/发帖等写操作 |
| 采集报告 | 文末统计数与正文条目数一致 |

## 10. 实施路线

| 阶段 | 交付物 | 验收 |
| ------ | ------ | ------ |
| P0 采集打通 | `collect-timeline.ts`（GraphQL 拦截）+ 登录态检查 | 手动运行一次，产出 raw JSON 且窗口闭合，耗时 < 3min |
