# Text Matrix 文章结束区体验重构设计与实施方案

## 文档信息

| 项目 | 内容 |
| --- | --- |
| 文档版本 | V2.2 |
| 更新时间 | 2026-08-27 |
| 状态 | 已实施（一步式续读：单推荐、准确来源标签、克制分享区、讨论独立呈现） |
| 适用范围 | `content/posts/**` 生成的文章详情页 |
| 目标读者 | 产品设计、前端开发、Hugo 模板维护者、内容运营 |
| 关联文档 | [Text Matrix 产品设计文档](./text-matrix-product-design.md)、[Giscus 评论实施方案](../comment/comment-system-architecture-design.md) |

本文定义文章正文结束之后、网站全局页脚之前的页面体验。目标不是增加点击，而是让已经读完文章的用户以最低成本继续理解当前主题，同时保留讨论、分享和自然离开的自由。

实施完成后应满足三个结果：

- 后续阅读只给出一个最可信的下一步；“参与讨论”独立可达但不争夺视觉重心。
- 推荐只在相关性可信时出现；无可信推荐时仍有主题或分类入口。
- 评论、推荐、埋点或 JavaScript 任一部分失败，都不影响正文和站内导航。

## 1. 最终决策

### 1.1 页面顺序

```text
正文
  ↓
收尾行：更新时间 · 分享 · 微博 · X
  ↓
后续阅读：0～1 篇高置信推荐 + 主题或分类全集入口
  ↓
参与讨论：说明 + Giscus
  ↓
网站全局页脚
```

完整评论区放在后续阅读之后。收尾行不再重复主题和讨论入口；读者先得到唯一、明确的向前路径，再自然进入独立评论区。悬浮评论按钮继续提供全页可达的快捷入口。

### 1.2 主次关系

| 维度 | 后续阅读 | 参与讨论 |
| --- | --- | --- |
| 产品角色 | 唯一主路径 | 高可达次路径 |
| 页面表达 | 无可见模块标题；一个推荐和一个全集入口 | 下方完整模块与悬浮快捷入口 |
| 成功判断 | 用户进入相关页面并产生有效阅读 | 用户到达可用评论区并产生输入或登录意图 |
| 失败降级 | 保留主题或分类入口 | 显示可操作的失败状态与外部入口 |

第一阶段不允许按文章类型反转主次，也不增加 `discussionFirst` 一类配置。若后续数据证明某类内容以讨论为主要价值，应单独立项，不在通用模板里增加隐式分支。

### 1.3 本次删除与保留

删除：

- “返回｜首页”；浏览器、顶部导航和页脚已经承担这些功能。
- 4 个静态“继续探索”胶囊。
- 文末全量标签；标签仍保留在文章元数据、标签页和搜索索引中。
- 默认 `.PrevInSection` / `.NextInSection`；发布时间相邻不代表阅读关系。
- 4 张带完整摘要的推荐卡片。
- 12 个并列的社交平台分享图标。
- 可见的“继续理解”标题、收尾行中重复的主题链接和讨论链接。
- 推荐项中重复的文章分类与多推荐列表。

保留：

- 最后更新时间。
- 一个上下文主题入口；没有结构化主题时回退到文章主分类。
- 一个“分享”操作，以及微博、X 两个纯静态分享入口。
- 最多 1 篇带准确来源标签的高置信推荐。
- 显式配置的系列下一篇作为最高优先级后续入口。
- 完整 Giscus 评论区。

本次不更换评论系统，不迁移 Discussion，不改变文章 URL、slug 或 Giscus 的 `pathname` 映射。

## 2. 第一性原理与设计边界

### 2.1 用户完成阅读后的状态

用户读到正文末尾时可能继续研究、表达观点、分享或离开。页面不应假设每个人都需要采取行动，也不能用高对比 CTA 制造被迫选择的感觉。

页面只主动解决一个问题：如果用户还想理解这件事，下一步去哪里。讨论和分享保持容易发现，但不能压过内容本身。

### 2.2 设计原则

1. **正确性高于覆盖率。** 没有可信推荐时显示 0 篇，不用弱相关内容凑数。
2. **结构表达语义。** 使用分隔线、标题和列表，不使用大卡片套小卡片。
3. **渐进增强。** 普通链接不依赖 JavaScript；分享和评论增强失败时提供替代路径。
4. **稳定高于聪明。** 内容关系由显式字段和结构化主题决定，不猜测用户意图。
5. **离开也是正常结果。** 不使用弹窗、吸底栏、自动展开或循环推荐阻碍退出。

## 4. 模块规格

### 4.1 收尾行

收尾行只显示两个信息组：

1. 最后更新时间。
2. 克制的分享区：“分享”按钮，以及微博、X 两个静态平台入口。

主题入口按以下顺序选择：

1. `topics` 的第一个值；通过 `data/topics.yaml` 链接到对应策展专题页。
2. `categories` 的第一个值；链接到对应分类页。
3. 两者都不存在或目标页无效时构建失败，不静默输出空链接。

文末不展示全部标签。标签继续服务内容组织和搜索，不再决定相关推荐，也不把作者的内部分类成本转移给读者。

分享区保留一个渐进增强按钮和两个明确的平台入口：

- 支持 `navigator.share` 时调用系统分享面板。
- 不支持时复制当前规范 URL，并在相邻的 `aria-live="polite"` 状态区显示“链接已复制”。
- 剪贴板调用失败时显示“无法自动复制，请从地址栏复制链接”。
- 微博、X 使用构建期生成的静态分享 URL，新窗口打开并带 `noopener noreferrer`。
- 页面加载时不请求微博或 X，不加载第三方分享 SDK；只有用户点击后才访问对应平台。

### 4.2 后续阅读

文章至少要有一个分类，因此后续阅读始终能渲染主题或分类全集入口；推荐可以为空。没有可信推荐时，全集入口自动成为主入口，不显示空列表、空标题或占位卡片。

推荐项最多一个，包含：

- 准确来源标签：“下一篇”“编辑推荐”或“同主题”。
- 完整文章标题，最多显示 3 行。
- 一个装饰性方向箭头，设置 `aria-hidden="true"`。

整行使用一个 `<a>`，不嵌套第二个交互元素。模块使用 `<nav aria-label="后续阅读">`，不显示“继续理解”或“推荐阅读”等重复标题，不分页、不轮播。

### 4.3 讨论入口与评论区

评论标题是片段目标和可编程聚焦目标：

```html
<section class="post-discussion" aria-labelledby="discussion-title" data-pagefind-ignore="all">
  <h2 id="discussion-title" tabindex="-1">参与讨论</h2>
  <p>使用 GitHub 登录。欢迎补充事实、异议与实践。</p>
  <!-- comment partial -->
</section>
```

点击悬浮评论入口后保留原生片段跳转。增强脚本在下一帧调用标题的 `focus({ preventScroll: true })`，确保键盘和辅助技术焦点同步到达。

评论关闭时，入口和完整评论区同时消失。评论说明提前披露 GitHub 登录要求，不把登录要求写成按钮文案，也不制造站内账号的错觉。

### 4.4 显式系列导航

普通文章不显示上一篇、下一篇。Frontmatter 明确配置 `next` 时，它替代其他推荐成为唯一主入口，并标记“下一篇”；`prev` 只保留为内容关系契约，不在文末增加向后操作。

目标页面不存在、自引用或前后重复时，构建必须通过 `errorf` 失败，不能静默输出空链接。

## 5. 推荐数据与算法

### 5.1 Frontmatter 契约

```yaml
topics:
  - ai-agent
relatedPosts:
  - /posts/another-article/
recommend: true
```

- `topics`：稳定的问题域，只使用受控词表中的 slug。
- `relatedPosts`：人工确认的文章路径；模板校验全部路径，只展示第一个有效页面。
- `recommend: false`：禁止该文章出现在任何自动推荐中。
- `recommend` 未填写时按 `true` 处理。

`topics` 不是标签的别名。标签可以具体到技术、人物和工具；主题回答“这篇内容帮助读者持续理解什么问题”。允许值维护在 `data/topics.yaml`，每项以 slug 为键，包含中文名称、专题 URL 和可选说明。

### 5.2 内容类型边界

第一分类决定内容类型。自动推荐只在相同第一分类内产生，防止行业快讯、视频精读和长期技术文章互相污染。

跨分类推荐只能通过 `relatedPosts` 显式配置。该例外是作者的可审查决定，不由模板推测。

### 5.3 单推荐决策规则

后续入口按以下优先级决策，命中即停止，最多返回 1 篇：

1. 有效 `next`，来源标签为“下一篇”。
2. `relatedPosts` 中第一个有效、非自身、未设置 `recommend: false` 的页面，来源标签为“编辑推荐”。
3. 与当前文章至少共享一个 `topics` 值、第一分类相同且相关度最高的页面，来源标签为“同主题”。
4. 没有可信候选时不显示推荐，主题或分类全集入口成为唯一主入口。

标签、分类和发布日期都不能单独创造候选。自动排序会随新内容加入而变化，这是预期行为；需要稳定目标时使用 `next` 或把目标放在 `relatedPosts` 第一位。

### 5.4 Hugo 配置

主题入口复用现有策展专题页，不再生成一套内容重复的 taxonomy 页面。`data/topics.yaml` 提供稳定映射：

```yaml
ai-agent:
  title: AI Agent 学习路径
  url: /ai-agent/
```

Related Content 只允许结构化主题产生候选：

```toml
[related]
  includeNewer = true
  threshold = 80
  toLower = true

  [[related.indices]]
    name = "topics"
    weight = 100
```

模板在调用 `.Related` 前先把候选集合限制为相同第一分类，并通过 options map 把本次查询的 `indices` 明确限制为 `topics`。结果合并阶段排除当前页、重复页和 `recommend: false`。不得退回“共享任意标签即可推荐”的旧逻辑。

### 5.5 内容迁移

上线前先为高访问、常青和承担专题入口的文章补充 `topics`。迁移不要求一次覆盖全部存量：未标注文章仍有分类入口，不会出现错误推荐。

内容检查必须阻断以下情况：

- 文章没有分类。
- `topics` 使用受控词表之外的值。
- `relatedPosts` 指向不存在页面、自身或重复路径。
- `recommend: false` 的页面被显式关联。
- `prev` / `next` 目标不存在、自引用或重复。

## 6. 评论加载与失败恢复

### 6.1 加载策略

Giscus 改为 `inputPosition = "top"` 和 `lazyLoading = true`。评论区进入视口前约 800px 时开始加载；点击“参与讨论”时立即开始加载。正文、主题入口和推荐不等待第三方脚本。

使用四态模型：

```text
idle → loading → ready
                 ↘ failed
failed → loading（用户主动重试）
```

状态定义：

- `idle`：尚未接近评论区，不加载第三方脚本。
- `loading`：显示“正在加载讨论…”，状态容器使用 `aria-live="polite"`。
- `ready`：Giscus iframe 已触发 `load`，或收到来源为 `https://giscus.app` 的有效消息。
- `failed`：脚本错误、iframe 错误或开始加载后 12 秒仍未就绪。

脚本自身的 `load` 事件不能代表评论就绪。监听器和 `MutationObserver` 必须在插入 Giscus 脚本之前建立，避免漏掉 iframe 创建与加载事件。

### 6.2 失败状态

失败后显示：

```text
讨论暂时无法加载。
[重试] [前往 GitHub Discussions]
```

- 不自动重试；用户点击“重试”后重新发起一次完整加载。连续失败仍保留重试和外部入口。
- 每次重试先移除旧脚本、iframe、监听器和计时器。
- 外部链接始终包含 `target="_blank"` 和 `rel="noopener noreferrer"`。
- `<noscript>` 提供 GitHub Discussions 链接。
- 失败状态不隐藏评论标题，不改变推荐区域，不阻塞页面其他链接。

## 7. 视觉与交互规格

### 7.1 视觉方向

文章结束区延续 Text Matrix 的知识库气质：正文结束处的一条细分隔线继续成为“阅读路径”的视觉起点。除此之外不增加背景卡片、阴影、渐变或装饰插图。

唯一推荐采用透明背景和上下细分隔线。文章标题使用正文标题字体；来源、时间和状态文本使用现有辅助字体。不得为该模块引入新字体文件。

### 7.2 尺寸与层级

- 文章结束区上边距：`3rem`。
- 收尾行与后续阅读：`1.15rem`。
- 推荐与全集入口：`.2rem`。
- 推荐与评论标题：`3rem`，移动端不超过 `2.5rem`。
- 推荐链接最小高度：`4.5rem`；触控目标最小尺寸：`44px × 44px`。
- 推荐标题最多 3 行，使用 `overflow-wrap: anywhere`，flex 子项设置 `min-width: 0`。
- 评论标题设置 `scroll-margin-top`，数值覆盖固定导航高度和安全余量。

后续阅读不显示模块标题；来源标签和“参与讨论”标题使用小号辅助色，系统分享、微博、X 与全集入口的字号、字重、颜色不得高于推荐标题。均不使用实心按钮、描边卡片或持续动画。

### 7.3 状态与可访问性

- 所有链接和按钮提供明确的 `:hover`、`:active` 和 `:focus-visible` 状态。
- 不移除 outline；焦点颜色通过现有主题变量适配浅色和深色模式。
- 交互元素设置 `touch-action: manipulation`，点击高亮颜色明确配置。
- 只在 `transform` 或 `opacity` 上使用过渡；本模块默认不需要动画。
- 装饰图标设置 `aria-hidden="true"`；图标按钮必须有 `aria-label`。
- `layouts/_default/baseof.html` 中悬浮的返回顶部和评论图标补充 `aria-label`，不能只依赖 `title`。
- 页面必须保留浏览器缩放能力，不设置 `user-scalable=no` 或 `maximum-scale=1`。
- 深色模式下 Giscus、焦点环、分隔线和状态文本都要达到可辨识对比度。

## 8. 工程结构

所有新增和覆盖逻辑放在项目目录，不直接修改 `themes/LoveIt/`：

| 文件 | 职责 |
| --- | --- |
| `layouts/posts/single.html` | 控制正文、文章结束区和评论区顺序 |
| `layouts/partials/single/footer.html` | 渲染收尾行、一步式续读和显式下一篇 |
| `layouts/partials/single/related.html` | 决策唯一编辑/自动推荐并执行校验 |
| `layouts/partials/comment.html` | 提供评论容器和无脚本入口 |
| `assets/js/article-end.js` | 分享、焦点同步、评论状态机和事件上报 |
| `assets/css/_custom.scss` | 项目级布局、交互状态和主题覆盖 |
| `data/topics.yaml` | 受控主题词表 |
| `hugo.toml` | Related Content、分享和 Giscus 配置 |
| `scripts/validate_article_end.py` | 内容关系与生成 HTML 的自动断言 |

主题升级后只比较 LoveIt 的评论参数、主题切换消息和项目覆盖入口。项目逻辑不得依赖主题内部未公开的选择器，除 Giscus 固定容器外都使用项目自有 class。

项目级 `comment.html` 自行输出 Giscus 所需的 `data-*` 配置，但不再把 `commentConfig.giscus` 写入 LoveIt 的前端配置；这样主题脚本不会和 `article-end.js` 重复加载 iframe。`article-end.js` 同时接管深浅色切换后的 `setConfig` 消息。页面中任何时刻只能存在一个 Giscus 加载器和一个 `.giscus-frame`。

Giscus 主题使用其内置的 `light` / `dark` 名称；不得使用 LoveIt 或 Utterances 的 `github-light` / `github-dark`，否则会被 Giscus 视为非内置主题，导致浅色模式的颜色变量失效。外层容器同时提供对应底色，作为 iframe 加载和主题切换期间的对比度兜底。

## 9. 数据与实验

### 9.1 事件契约

只有文章结束区进入视口时才记录曝光，避免用全部文章会话稀释真实转化：

| 事件 | 触发条件 | 关键字段 |
| --- | --- | --- |
| `article_end_view` | 文章结束区首次进入视口 | `source_page`、`content_type`、`topic` |
| `article_continue_click` | 点击主题入口或推荐文章 | `target_kind`、`target_url`、`position` |
| `article_discussion_click` | 点击悬浮讨论入口 | `target_kind`、`target_url` |
| `article_comment_state` | 评论进入 `ready` 或 `failed` | `state`、`duration_ms`、`attempt` |
| `article_share` | 系统分享、复制结果，或点击微博/X | 系统路径使用 `method`、`state`；平台路径使用 `target_kind`、`target_url` |
| `article_read_engaged` | 目标文章正文可见累计 10 秒，且阅读进度达到 25% | `source_page`、`referrer_path` |

事件失败不能调用 `preventDefault()`、阻塞跳转或向用户显示统计错误。不得记录评论正文、GitHub 用户名、邮箱和剪贴板内容。

### 9.2 主指标与护栏

主指标：

- 有效继续率：发生 `article_continue_click`，且目标页在同一会话的 30 分钟内触发 `article_read_engaged` 的 `article_end_view` 占比。
- 主题回流率与推荐文章回流率分别统计，不能合并后掩盖其中一项下降。

次级指标：

- 讨论入口点击率。
- 评论 `ready` 率和中位加载时间。
- 分享成功率。

护栏：

- 评论失败率不得显著上升。
- 移动端文章结束区退出率不得恶化。
- 页面不能新增横向滚动、明显布局偏移或不可达链接。
- 评论点击率提高但有效继续率下降，不能判定改版成功。

### 9.3 验证顺序

1. 先在旧页面接入 `article_end_view`、继续点击和讨论点击，收集至少 14 天基线；样本不足时继续收集，不用低样本得出结论。
2. 按桌面/移动端、搜索/直接/外部来源、文章分类分层比较。
3. 先发布到 Preview，再对固定文章样本灰度检查，确认错误率和页面性能。
4. 全量发布后观察至少 28 天。没有随机实验基础设施时，只报告相关变化，不声称因果提升。

## 10. 自动验证与验收

### 10.1 构建与内容校验

构建命令必须使用仓库固定的 Hugo 版本并把警告视为失败：

```bash
hugo --panicOnWarning --gc --minify
python3 scripts/validate_article_end.py public
```

`validate_article_end.py` 对每篇文章断言：

- 唯一一个带 `aria-label="后续阅读"` 的 `nav` 和最多一个评论区。
- 推荐数量为 0～1，来源只能是 `next`、`editorial` 或 `related`，且不含自身、无效 URL 和 `recommend: false` 页面。
- 恰好一个主题或分类全集入口、一个系统分享按钮，以及微博、X 两个静态平台入口；不恢复可见的“继续理解”标题。
- 每个主题、分类、系列与显式推荐目标都存在。
- 评论开启时，页面内有唯一的 `#discussion-title` 和 Giscus 根容器；评论关闭时二者同时不存在。
- 不存在空 `href`、`javascript:void(0)` 或只有图标而没有可访问名称的链接。
- 新窗口链接包含 `noopener noreferrer`。

内容字段校验应直接读取 Frontmatter 和 `data/topics.yaml`；生成 HTML 校验使用标准 HTML 解析器，不用正则表达式代替 DOM 断言。

### 10.2 浏览器验收

固定测试 6 类文章：有显式推荐、有主题自动推荐、无主题、评论关闭、超长标题、系列目标错误。桌面使用 `1440 × 1000`，移动端使用 `390 × 844`。

必须通过：

- 正文结束后 1 屏内出现唯一后续入口和“参与讨论”。
- 评论区视觉权重低于后续入口，悬浮入口的键盘和触控路径可达。
- 点击讨论入口后，标题位于可视区域上半部并获得焦点。
- 单条推荐与全集入口在移动端总高度不超过 `160px`。
- 浅色、深色、200% 缩放和 320px 宽度下无横向滚动。
- Giscus 被网络规则拦截后，12 秒内进入失败状态；重试和外部入口可用。
- JavaScript 禁用时，主题、分类、推荐、系列和评论外部入口仍可使用。
- 分享成功、拒绝和剪贴板失败都有准确反馈。

### 10.3 性能预算

- 文章结束区不增加图片、Web Font 或第三方分享脚本；微博/X 仅使用静态链接。
- Giscus 在接近评论区或用户主动跳转前不加载。
- 推荐在构建期生成，浏览器不请求推荐 API。
- 新增项目脚本压缩后目标不超过 8KB；超过时必须说明原因并拆除非必要功能。
- 对文章样本比较改版前后的布局偏移和主线程工作；不得以视觉简化换取更多运行时代码。

## 11. 实施顺序

### 阶段 0：建立基线与内容契约

1. 在旧页面接入文章结束曝光、继续点击和讨论点击。
2. 创建 `data/topics.yaml`，确定首批受控主题。
3. 为高访问和常青文章补充 `topics`，校验显式关系和系列关系。
4. 同步修订产品设计文档与 Giscus 文档中的冲突描述。

完成条件：基线事件可用，主题词表通过检查，文档只有一套配置事实。

### 阶段 1：模板与推荐

1. 删除重复导航、全量标签、社交图标组和默认上下篇。
2. 增加主题或分类兜底入口。
3. 实现 `next`、编辑推荐、同主题推荐依次择一的决策算法。
4. 用 `errorf` 阻断无效的显式推荐和系列路径。

完成条件：所有文章都有稳定的后续阅读入口；自动推荐不会由单个宽泛标签产生。

### 阶段 2：评论、分享与无障碍

1. 评论输入框移到顶部并启用延迟加载。
2. 实现评论四态模型、用户主动重试和可操作失败状态。
3. 实现系统分享按钮、非阻塞反馈，以及微博/X 静态分享入口。
4. 修复锚点焦点、悬浮图标名称、触控与深色模式。

完成条件：第三方脚本失败时页面仍完整可用；键盘、触控和无脚本路径通过验收。

### 阶段 3：自动化、灰度与发布

1. 把内容关系和生成 HTML 断言接入 CI。
2. 完成桌面、移动端、深色模式、缩放和网络失败测试。
3. Preview 验证后灰度检查固定文章样本。
4. 全量发布并按 28 天窗口复盘，不用单项点击率提前宣布成功。

## 12. 回滚与维护

模板、样式、脚本和配置应作为一个提交单元发布。出现以下任一情况立即回滚：

- 构建失败或内容链接大面积失效。
- 评论 `ready` 率明显下降且无法在一个修复周期内恢复。
- 移动端出现横向滚动、焦点不可见或正文后的主路径不可达。
- 推荐出现跨内容类型的大量错误结果。

回滚只恢复展示实现，不能删除新增的 `topics` 和 `relatedPosts` 内容数据。评论仓库、Discussion、URL 映射和历史数据不受回滚影响。

维护规则：

- 新主题先加入 `data/topics.yaml`，再用于文章 Frontmatter。
- 每月抽查高访问文章的主题入口和唯一推荐。
- 主题升级后运行完整构建、HTML 断言和浏览器验收。
- 指标字段一旦发布不按视觉文案改名；需要变更时增加版本字段。
- 连续两个观察周期无使用且无产品价值的辅助操作应删除，不保留装饰性功能。

## 13. 发布门槛

以下条件全部满足后才可全量发布：

- 主路径、次路径和无推荐降级规则已实现。
- 旧页面基线已经建立。
- 主题词表、显式推荐和系列关系通过构建校验。
- 推荐不会由标签单独产生，且最多 1 篇并带准确来源标签。
- 评论状态机不会把“脚本已加载”误判为“评论已就绪”。
- 评论失败、JavaScript 禁用和评论关闭场景可用。
- 锚点焦点、键盘、触控、缩放、深色模式和长标题通过测试。
- 自动 DOM 断言进入 CI，不以人工 `rg` 输出代替验收。
- Preview 与固定文章样本没有回归后再全量发布。
