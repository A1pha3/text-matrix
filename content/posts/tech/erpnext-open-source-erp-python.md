ERPNext 不是一个小项目。GitHub 上它已积累超过 3.6 万 Stars、约 1.2 万 Forks，背后有 Frappe 这家公司在维护。它的定位不是某一个管理小工具，而是把一家公司的财务、库存、采购、销售、项目、人事塞进同一套系统。

关键判断是：**如果你需要一个开源 ERP，并且团队愿意留在 Python 生态，它是目前最值得认真评估的候选；但如果你只有几个人、需求很简单，它大概率是过度工程。**

## 系统地图

ERPNext 的价值不在于某一个模块，而在于所有模块共享同一套数据。一张销售单被确认后，会同时牵动库存、应收、项目和报表，不需要人工在几套软件之间搬运数据。

```
┌─────────────────────────────────────────────────────────────────┐
│                          ERPNext                                │
│                      功能模块（共享同一数据）                      │
├─────────────────────────────────────────────────────────────────┤
│  财务会计  │  订单与库存  │  制造  │  资产管理  │  项目与人力       │
│  总账      │  销售/采购单 │  BOM  │  购买到处置 │  项目/工时       │
│  应收/应付 │  补货与交付  │  工单  │  折旧       │  员工/薪资/请假  │
│  成本/预算 │  供应商管理  │  分包  │  维护计划   │                 │
├─────────────────────────────────────────────────────────────────┤
│                    底层框架（Frappe 生态）                        │
│        Frappe Framework (Python) + Frappe UI (Vue)              │
└─────────────────────────────────────────────────────────────────┘
```

## 核心能力

### 财务会计

- 总账（GL）、应收账款（AR）、应付账款（AP）
- 成本中心与预算控制
- 财务报表生成、多币种、多公司核算

### 订单与库存

- 库存跟踪与安全库存预警
- 销售订单、采购订单、供应商管理
- 批次 / 序列号级追溯，货运与交付跟踪

### 制造

- BOM（物料清单）管理、工单系统
- 产能规划、委外分包、物料消耗跟踪

### 资产管理

- 资产从购买、折旧到处置的全生命周期
- IT 设备登记与维护计划

### 项目与人力

- 任务拆解、工时记录、项目预算与盈利跟踪
- 员工管理、招聘、薪资、请假

## 技术架构

ERPNext 建在 Frappe 生态之上，这是它区别于多数 ERP 的关键：

1. **Frappe Framework**：Python 全栈低代码框架。所有数据模型都叫 DocType，字段、链接、权限、校验都以元数据形式存储，而不是写死在代码里。管理员能在界面里加字段、加表单，甚至定义全新的业务单据类型，几乎不用写代码。每次新建 DocType，列表、表单、REST API、权限、报表会自动生成。
2. **Frappe UI**：Vue 驱动的现代前端，自带响应式布局。

这个"模型即元数据"的设计，让定制变成一层叠加在核心之上的东西，升级时不容易被自定义代码拖累。这也是 ERPNext 不需要 fork 源码就能深度改造成的原因。

数据库默认用 MariaDB（MySQL 兼容），也可接 PostgreSQL。

## 一张销售单如何走完链路

把抽象结构落到一次真实操作里，整个系统就好懂了。假设你卖出一批商品：

1. 你在销售模块创建一张**销售订单**，商品、数量、价格、付款条件都写进去。
2. 系统据此预留库存，并生成对应的**交货单**与**送货单**；库存台账自动扣减。
3. 交货完成，系统生成**销售发票**，应收账款（AR）入账。
4. 应付、收取的款项再被归集到总账，生成**利润 / 现金流报表**。
5. 如果这笔销售还挂在一个项目下，其成本会和**项目预算**联动，项目盈利实时更新。

全程不需要你在库存软件、财务软件、报表工具之间手动搬运数据。这就是"共享同一数据"的意思。

## 安装与部署

### Frappe Cloud（托管）

官方托管服务，安装、升级、监控、备份都由 Frappe 处理，从约 5 美元 / 站点 / 月起，按需付费，提供 14 天免费试用。适合没有运维能力的团队。

### Docker（自托管，推荐）

官方 Docker 仓库是 `frappe/frappe_docker`，用 Compose 一条命令起全套服务（MariaDB、Redis、Nginx、应用服务）：

```bash
git clone https://github.com/frappe/frappe_docker
cd frappe_docker
docker compose -f pwd.yml up -d
```

初始化完成后浏览器访问 `http://localhost:8080`，默认账号为 `Administrator`。

### Bench（手动安装）

Bench 是 Frappe 官方的命令行工具。先通过 pip 安装（不是 npm）：

```bash
pip3 install frappe-bench
```

初始化 bench、创建站点并安装 ERPNext：

```bash
bench init erpnext-bench
cd erpnext-bench
bench new-site mysite.localhost --admin-password admin
bench get-app erpnext
bench --site mysite.localhost install-app erpnext
bench start
```

ERPNext 与 Frappe 一起版本化，当前大版本为 16（2026 年 1 月发布），更早的 14 已停止维护。生产环境建议用 Docker 或官方安装脚本，手动 bench 更适合开发。

## 适用边界

**适合用：**

- 中小企业需要一套完整 ERP，希望财务、库存、项目一体化
- 团队已有 Python 技术栈，想做深度定制
- 需要开源、避免供应商锁定，且愿意接受 GPL 约束
- 有基本的运维能力，或愿意为 Frappe Cloud 付费托管

**不太合适：**

- 团队少于 10 人、只是偶尔开张发票——轻量工具更划算
- 期望零配置、开箱即用——它需要一定的定制才能贴合具体流程
- 完全没有运维能力也没预算上云——自托管会变成持续负担
- 行业有强监管合规要求（如银行、保险、医疗），需要先确认合规细节是否满足

## 与竞品比较

| 维度 | ERPNext | Odoo | Tryton |
|------|---------|------|--------|
| 主项目 License | GPL-3.0 | LGPL | GPL |
| 底层框架 License | MIT（Frappe Framework） | 拥有 Odoo 社区版 | 自有框架 |
| 语言 | Python | Python | Python |
| 模块覆盖 | 财务/库存/制造/项目/人力 | 最广，含营销、电商 | 基础 + 财务 |
| UI | 现代 Vue | 老派但成熟 | 基础 |
| 社区与生态 | 大，Frappe 系列应用丰富 | 很大，插件市场庞大 | 中等 |
| 托管 SaaS | Frappe Cloud | Odoo Online | 无官方 |

一句话结论：**ERPNext 胜在"完全开源 + 现代前端 + 低代码定制"**，Odoo 胜在生态与第三方应用数量，Tryton 更轻但在功能覆盖上最弱。选型时先确认你用不用得上 Odoo 那些额外模块，别被功能数量牵着走。

## 自测题

想确认自己是否真正读懂了，先把下面几个问题在心里过一遍，再对照参考答案。

1. **为什么 ERPNext 的"模型即元数据"设计重要，而不是换个说法重复它的功能清单？**
   - 它意味着新增字段、表单甚至整类业务单据都无需改代码、无需 fork 源码，定制以叠加层形式存在，升级时不会被自定义代码拖累。
2. **一张销售订单被确认后，会联动哪些模块？**
   - 库存扣减、交货/送货、销售发票与应收入账，若挂在项目下还会联动项目预算与盈利。
3. **ERPNext 的许可证是 MIT 吗？**
   - 不是。ERPNext 主项目是 GPL-3.0，只有底层 Frappe Framework 是 MIT。
4. **三种部署方式各适合什么场景？**
   - 无运维能力用 Frappe Cloud；要完整控制或生产环境用 Docker（frappe_docker）；开发调试用手动 bench。

## 进阶路径

1. **先部署再配置**：在 Frappe Cloud 免费试用或 Docker 起一套，配置公司信息、科目表、仓库、基础数据。目标是让系统先跑起来。
2. **再理解模块**：逐个过一遍会计（科目表、税务）、库存（仓库、补货规则）、项目（任务类型、计费）的配置，直到能用它管理你真实业务的 80%。
3. **然后做定制**：用 DocType Builder 在界面里创建一个新类型（如"设备维修单"）并配置权限和工作流；需要更多时再学 Frappe 框架，写 Controller、自定义报表和 API。
4. **最后才上生产**：在云服务器上用 Docker 或官方脚本部署，配置 Nginx、SSL、自动备份与监控。生产部署在确认流程稳定之后再做，别在系统还没理顺时急着扩容。

## 结论

ERPNext 是 Python 生态里最认真的开源 ERP。它的竞争力来自完整的功能覆盖、现代的 Vue 前端，以及"定制不改源码"的 Frappe 框架。

但它不是万能药。判断标准很简单：你的业务值不值得一套完整的 ERP，和你有没有人力 / 预算把它跑顺。先花几十块上 Frappe Cloud 免费试用，跑一遍真实的销售单，再决定要不要自托管。
